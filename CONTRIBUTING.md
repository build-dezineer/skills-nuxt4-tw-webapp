# Contributing

This repository publishes Dezineer's webapp skills as portable
[Agent Skills](https://agentskills.io). Every change must keep the collection
**spec-compliant, self-contained, and installable by any skills-capable agent**.

Start with the standard's own guidance before authoring:

- [Specification](https://agentskills.io/specification) — format requirements
- [Best practices](https://agentskills.io/skill-creation/best-practices) — scoping and instruction design
- [Evaluating skills](https://agentskills.io/skill-creation/evaluating-skills) — test cases and iterations
- [Optimizing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions) — triggering accuracy

## Setup

Requires Node.js 20+ and [uv](https://docs.astral.sh/uv/).

```bash
npm ci
npm run validate        # repo checks: frontmatter, links, no host keys
npm run validate:spec   # official skills-ref validation
npm run index:check     # skills/index.json is fresh
```

## Repository layout

```
skills/<name>/SKILL.md      # required
skills/<name>/references/   # detail loaded on demand (when the skill says to)
skills/<name>/evals/        # evals/evals.json test cases
skills/index.json           # generated by scripts/build-index.mjs — do not hand-edit
```

Skill folders do not ship executable `scripts/`; the published skills are guidance
plus static assets only. Deterministic checks live in the consuming app.

## Frontmatter contract

Only Agent Skills spec fields are allowed. Unknown keys fail CI — including
client-specific extensions.

```yaml
---
name: table
description: >-
  Full data table covering sorting, filtering, pagination, CSV export, row selection,
  expandable rows and column visibility, built on the pre-built `DataTable` +
  `useDataTable` + `DataTablePagination`. Handles loading, error, empty and data states.
  Use for any admin or list screen showing 5+ tabular rows.
license: Apache-2.0
compatibility: >-
  Requires a Dezineer-scaffolded Nuxt 4 project (Tailwind v4 design tokens, shared
  components, media pipeline). Guidance targets Dezineer's generator; patterns may
  transfer to a plain Nuxt project with those primitives.
metadata:
  version: "1.0.0"
  tags: "data, tables, listing"
  stack: "nuxt4, vue3, tailwind4, radix-vue, lucide"
---
```

| Field | Rules |
|---|---|
| `name` | Required. Must equal the folder name: `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤64 chars. |
| `description` | Required. 1–1024 chars (target 250–500). See the formula below. |
| `license` | Always `Apache-2.0`. |
| `compatibility` | ≤500 chars. The sentence above on every skill. |
| `metadata.version` | Semver string. Start at `"1.0.0"`; see versioning. |
| `metadata.tags` | Comma-separated search tags, ≤4 tokens. |
| `metadata.stack` | Comma-separated stack tokens from the vocabulary below. |

`metadata` values must be strings. `compatibility` is the human/agent-readable
statement; `metadata.stack` is its machine-readable twin.

### Stack token vocabulary

Base tokens on every skill: `nuxt4`, `vue3`, `tailwind4`.
Add library tokens **only when the skill's code actually uses them**: `radix-vue`,
`vueuse`, `gsap`, `swiper`, `tresjs`, `three`, `chart.js`, `lucide`, `lenis`,
`split-type`. Lowercase, ≤8 tokens.

## Writing the description

The description is the only thing an agent sees before deciding to load the skill, so
it carries the entire triggering burden. Use the formula:

> **1 sentence on what it builds + 1 sentence on when to use it + flavor coverage.**

- Include the words a user or agent would search for: surface name, framework,
  component names, `"Use when …"`.
- Be specific about coverage ("collapsible, icon rail, floating and overlay variants"),
  not marketing copy.
- No Dezineer-internal jargon where a general term works.

Examples:

```yaml
# table
description: >-
  Full data table covering sorting, filtering, pagination, CSV export, row selection,
  expandable rows and column visibility, built on the pre-built `DataTable` +
  `useDataTable` + `DataTablePagination`. Handles loading, error, empty and data states.
  Use for any admin or list screen showing 5+ tabular rows.

# metric-card
description: >-
  KPI/stat cards using the pre-built, protected `MetricCard`: default, icon, sparkline,
  progress and hero variants with count-up animation and hover elevation already wired
  in. Covers grid composition and variant mixing. Use on any dashboard page that
  surfaces KPI numbers.
```

## Writing the body

The body is loaded whenever the skill activates, so every line must earn its place.

- Keep `SKILL.md` **under 500 lines**. Move detail to `references/` and say **when**
  to load each file ("Read `references/variants.md` before writing `SidebarNav.vue`"),
  one level deep.
- Add what an agent would get wrong without you: project conventions, non-obvious
  edge cases, exact component APIs. Omit what a capable model already knows.
- Prefer imperative, generalizable procedures over task-specific answers.
- Prefer a clear default over a menu of equal options; mention escape hatches
  briefly.
- Keep the highest-value corrections in a `## Non-negotiables` section in `SKILL.md`.
- Use concrete templates for required output shapes and checklists for multi-step
  workflows.
- Cross-skill references are relative links from the skill root, e.g.
  `../media/SKILL.md`.
- Do not include host-specific keys, product-internal paths, or `dezineer-`
  identifiers. Scaffold paths required for the pattern are allowed; internal jargon
  is not.

## Versioning

- New skill: `1.0.0`.
- Wording, examples, or references change: bump patch (`1.0.1`) or minor (`1.1.0`)
  depending on scope.
- The skill's inputs or section contract change (renamed wizard answers, changed
  component API, different file surface): bump major (`2.0.0`).
- Update `metadata.version` and regenerate `skills/index.json`. Repo tags pin
  snapshots for vendoring consumers.

## Evals

Add `evals/evals.json` when the skill's output is objectively verifiable (files,
markup, required component usage). Subjective qualities (visual polish, copy) are
reviewed by humans instead.

```json
{
  "skill_name": "table",
  "evals": [
    {
      "id": 1,
      "prompt": "A realistic user message, with file paths and context.",
      "expected_output": "What success looks like, in observable terms.",
      "files": [],
      "assertions": ["Programmatically or visually checkable statement"]
    }
  ]
}
```

Run evals with Anthropic's
[`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator),
or manually: run each prompt twice — with the skill and without it (the baseline) —
then grade outputs against the expected results. Keep iteration workspaces out of
git (`*-workspace/` is gitignored).

## Pull request checklist

- [ ] `name` matches the folder and follows the naming regex.
- [ ] `description` follows the formula and is ≤1024 chars.
- [ ] Frontmatter uses only spec fields (`validate-skills.mjs` enforces this).
- [ ] `SKILL.md` is under 500 lines, or split into `references/` with when-to-load
      guidance.
- [ ] Cross-skill and file references resolve; no `dezineer-` identifiers.
- [ ] `metadata.version` bumped correctly and `npm run index` run.
- [ ] `npm run validate`, `npm run validate:spec`, and `npm run index:check` pass.
- [ ] Evals added or updated if the output is objectively verifiable.
